# 0015. Manage the database schema with Alembic migrations

## Status
Accepted (2026-11-04). Supersedes ADR 0007.

## Context
Tables are created with `create_all` when the app starts (ADR 0007).
`create_all` only creates missing tables; it never changes existing ones,
so a new column (for example for achievements) would need the database to be deleted.
The app now runs on PostgreSQL (ADR 0014) and keeps data between runs,
so schema changes must keep the existing data.

## Decision
Alembic manages the database schema. Every model change comes with a migration,
generated with `alembic revision --autogenerate`, reviewed by hand and committed with the change.
Alembic reads the database URL from the app settings (ADR 0006).

The app does not change the schema when it starts: `create_all` is removed from the startup.
Migrations run as a separate step before the app starts:
`alembic upgrade head` locally, and a CI step before the tests.

The test database is built with `alembic upgrade head` once per test run.
Each test runs inside a transaction that is rolled back at the end,
so every test starts with empty tables.
CI runs `alembic check`, which fails when the models and the migrations do not match.

## Alternatives considered
- **Keep `create_all` on startup**: no extra step, but existing tables can never change.
- **Run migrations when the app starts**: simpler for a single local user, but the schema
  changes silently, several app instances would run them at the same time,
  and a failed migration would block the startup. Deployments usually run migrations
  as a separate step.
- **`create_all` for the test database, plus one test for the migrations**: simpler,
  but most tests would run on a schema that the migrations did not build.
- **Drop and recreate the tables for every test** (the current setup): with migrations
  this is slower than rolling back a transaction.

## Consequences
- Schema changes keep the existing data.
- Every model change needs a migration; CI fails if one is missing.
- Running the app locally needs one more step, `alembic upgrade head`, documented in the README.
- Autogenerated migrations must be reviewed: Alembic cannot detect every change
  (for example, a renamed column looks like a dropped column and a new one).
- The existing local database is marked as up to date with `alembic stamp head`, without losing data.
- The startup test (`test_main.py`) is removed; `alembic check` and the migrated test database
  take its place.
